JavaScript 运行机制：从执行上下文到事件循环与 DOM 冒泡

前言

今天初探了一下js的运行机制，茅塞顿开，天光乍现，熠熠生辉，何其有幸，咕咕嘎嘎，比比拉布……有感而发，遂有此篇……

js是如何编译

现代 JavaScript 引擎（如 edge 内置的V8/node.js）并不是在代码运行前编译好的，而是在代码即将运行和正在运行的过程中进行编译和优化，这一部分比较复杂，我们只需要知道在代码运行前，引擎会在内存中预留一部分作为 js 运行的空间，下面就介绍这个空间是怎么搭建的。

创建阶段
  • 创建全局对象和this：在浏览器中，引擎会创建window对象，并且把this指向它。
  • 建立作用域链 ：确定当前代码可以访问哪些外部变量。
  • 内存分配与变量提升 ：引擎会寻找所有函数声明和变量声明
    • 函数会完整存入内存
    • var 声明 会存入内存并且初始化为undefined(变量提升)
    • let 和 const 也会被分配内存，但不会被初始化，形成暂时性死区 TDZ ，不重要，你只需要知道 （这就是为什么你可以在函数声明之前调用函数，或者在 var 声明之前访问它会得到 undefined 的原因）。
执行阶段

在继续介绍前，先解释一个概念 执行上下文

  • 内存分配并不是杂乱无章的。引擎需要一个容器来管理这些分配好的变量和函数，并确定它们之间的调用顺序和访问权限。执行上下文就是这个容器。它不仅包含了我们刚刚提到的内存空间（存放变量和函数），还绑定了逻辑关系（比如 this 指向谁、去哪里找外部变量，没错就是创建阶段提到的创建全局对象和this，建立作用域链，内存分配与变量提升。

环境搭建好后，引擎才开始从上到下逐行执行代码，为变量赋真实的值，并执行函数调用。

  • 当程序运行时，会产生很多个执行上下文（全局一个，每个被调用的函数各一个）。JavaScript 是单线程的，它通过 调用栈 来管理这些上下文：
    • 程序启动，全局执行上下文 被推入栈底。
    • 当你调用一个函数时，引擎会为该函数创建一个新的执行上下文，并将其压入栈顶。
    • JS 引擎永远只执行栈顶的上下文。
    • 函数执行完毕后，它的上下文会被弹出栈（销毁），控制权交还给它下面的上下文。

js的生命周期有何特殊

很简单，只要这个执行上下文内的变量还有被外部引用，他就永远保存在堆内存中。

为何要特殊处理

在复杂的前端交互中，我们经常需要跨越函数的生命周期来保留某些状态（比如计数器、组件状态等），为了实现这一点，JS 巧妙地利用了作用域的机制。

  • 快照机制：词法作用域就像照相机。我们只需要知道函数在被定义的那一刻，就将周围的环境变量 拍成了快照，保存在内存中，而不受它最终在哪儿被调用的影响。

单线程如何表现得像并发一样优雅

既然 JS 主线程只有一个，如果遇到耗时的网络请求或定时器，那要怎么处理呢，要如何保证流畅性呢，并且一个网页总是在运行中的，又要如何保证代码不会走到头呢，这就要提到建立在异步上的机制了

事件循环是 JavaScript 实现非阻塞、异步编程的核心运行机制。

你可以理解为，它时刻监听主线程的状态，并在合适的时机将准备好的回调函数调度到主线程中执行。 借此，JS 才能在单线程的限制下，丝滑地处理各种网络请求和用户交互。

简单来说，事件循环由三个部分组成

  • 执行栈:主线程的工作区,所有的同步代码都会被压入这个栈中，只要栈里还有代码，主线程就会一直忙碌。
  • Web APIs / Node APIs:既然主线程不能被阻塞，那耗时的任务交给谁呢？交给浏览器（或 Node 环境）。当遇到 setTimeout、fetch 网络请求、DOM 事件监听时，主线程会把它们直接甩给 Web APIs 去后台处理（比如倒计时、发网络包），主线程自己则继续往下执行其他同步代码。
  • 任务队列:当 Web APIs 里的耗时操作完成了（比如定时器时间到了，或者接口数据回来了），它不能直接去打断正在执行栈里干活的主线程，而是把对应的回调函数推入这个任务队列中排队等待,注意是将回调函数加入队列，并且只是排队，理解这点很重要
它们是如何协同工作的
  • 主线程开始执行脚本，把所有的同步任务按顺序放入执行栈中运行
  • 遇到异步任务，主线程把它交给 Web APIs 去处理，然后继续执行后续的同步代码。
  • Web APIs 处理完异步任务后，把它的回调函数放入任务队列中
  • 当且仅当执行栈被完全清空时，事件循环就会去检查任务队列。
  • 如果任务队列里有排队的回调函数，事件循环就会把队列里的第一个函数推入执行栈，让主线程执行。
  • 执行完这个函数后，执行栈再次清空，事件循环再去检查任务队列……如此往复，形成循环。

    如果要继续探索任务队列的运行机制，可以了解一下宏任务和微任务

浏览器还在其中扮演什么角色

上面说到浏览器会帮js处理异步任务，浏览器也是真实dom存放的地方，
这里有个比较有意思的冒泡机制想讲解一下

假设有这样一个代码场景
假设有这样一个代码场景：我们在页面上嵌套了三个元素（爷爷、爸爸、儿子），并且给他们每个人都绑定了点击事件。

  • 当我们用鼠标只点击了最里面的“儿子”按钮时，控制台的输出
    儿子：我被点击
爸爸：谁点了我
爷爷：我被点到了
  • 这就是冒泡机制（Event Bubbling）。在 DOM 中，事件就像水底吐出的一个气泡，从最深处的那个目标元素（目标阶段）开始触发，然后一路沿着 DOM 树向上传递，依次触发父元素、祖父元素绑定的同类事件，直到最外层的 document 或 window。
  • 有时候我们就是只想让child响应事件，不想触发别的事件（比如点击弹窗内部，不想触发底层的关闭弹窗事件）。这时候，我们只需要在“child”的事件回调里加上：
    • event.stopPropagation();//阻止事件继续向上传播
